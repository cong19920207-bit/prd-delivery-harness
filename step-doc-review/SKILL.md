# STEP 文档审查、修正与复审

## 手动触发

仅在用户显式调用 `$step-doc-review` 或明确点名 `step-doc-review` 时使用。普通谈话中提到 STEP、覆盖率、遗漏、幻觉或需求比对，不自动触发。

## 核心原则

先用 PRD 和可验证事实做全量审查，只修证据能唯一确定的问题，再从原始来源完整复审。不得用“最佳判断”替用户选择业务语义，也不得覆盖用户原 STEP。

## 入口与模式

- `standalone`：用户直接调用本 Skill；按意图选择 `review-only` 或 `review-repair`，输出本阶段结果后结束，不自动进入下一阶段。
- `review-only`：只输出首次完整审查报告，不改 STEP。
- `review-repair`：用户明确要求修正时，保留原文并生成新修正版、首次报告和 Diff，再完整复审。
- `orchestrated`：由 `$prd-delivery-harness` 在 Phase 2 读取本 Skill 后执行；不做重复流程确认，自动修正确凿问题并完整复审，将结果交回总控。

用户已经确认输入并要求继续时，不再要求重复确认。仍缺少 PRD、STEP 正文或判断必需来源时，直接返回对应阻断结果。

## 输入与来源

支持本地路径、可访问仓库链接、PDF、Word、Markdown、纯文本和文本粘贴。至少需要原始 PRD 与 STEP 草稿；代码/契约按文档中引用的路径和符号定向读取。

事实优先级：

1. `USER_DECISION`
2. `PRD`
3. `CONTRACT`
4. `REPO_BASELINE`
5. 项目规范
6. 派生 STEP 与审查报告

统一来源标签：`USER_DECISION`、`PRD`、`CONTRACT`、`REPO_BASELINE`、`RUNTIME`、`PLANNED`、`UNVERIFIED`。用户提供并明确标为 PRD 或仓库核实证据的内容，按其实际证据类型记录；无法验证的代码事实必须标 `UNVERIFIED`。没有 `RUNTIME` 证据时，不声称线上行为已验证。

## 完整审查

首次审查和每轮修正后的完整复审都必须覆盖以下九维，不能只检查 Diff。

### 维度 1：幻觉检查

查找无来源的字段、值、状态、错误码、业务顺序、实现细节、路径、符号、测试要求和完成标志。

### 维度 2：遗漏检查

逐项检查需求、验收、排除项、禁止项、技术债和 PRD 明示的文档动作是否有 STEP 处置。

### 维度 3：冲突检查

检查 STEP 与 PRD、用户决定、必要契约和代码基线是否存在可测试矛盾；代码基线不能反向取消 PRD。

### 维度 4：不清晰检查

查找多义选择、笼统完成标志、无核实目标的“待查”、不存在的引用和无法执行的描述。

### 维度 5：依赖顺序合理性

检查缺失、多余、断链和循环依赖，以及被隐藏的文件、数据、接口或契约依赖。

### 维度 6：验收标准可测性

每个完成标志必须能由具体输入、行为或断言验证；“功能正常”“测试通过”本身不够。

数量断言不能代替对象一致性：当验收要求“这些记录/对象/字段”时，必须比较同一输入快照下的记录身份、稳定标识或相关字段值，而不只是数量相同。PRD 未要求顺序时不得擅自增加顺序要求。

仅重述“CSV 恰好是这 N 条”或“包含这些记录”仍不是可执行的对象比较方法。验证版必须明确写出比较键或投影：优先比较稳定 ID 的集合/多重集；没有稳定标识时，比较全部相关可见字段组成的元组多重集。缺少这类明确方法时不得返回 `PASS` 或 `PASS_WITH_RISKS`；`orchestrated`/`review-repair` 必须补齐后重审，`review-only` 返回 `FAILED_VALIDATION`。

验收若明确限定某类请求、系统层级或可观察输出，只能由直接验证该对象和结果的 STEP 覆盖。相关但未要求的 UI 呈现、客户端拦截、重试或日志等实现细节不得当作该验收的组成部分，也不能反向映射该 ID。例如只要求服务端请求返回 403 时，不得据此推导按钮隐藏/禁用；若确需该行为，必须有 PRD 或 `USER_DECISION` 来源。

### 维度 7：PRD 决策覆盖率

逐条映射所有有效需求/决策 ID 到 STEP，包含安全硬约束和禁止项。

### 维度 8：技术债标注完整性

逐条核实 PRD 明示技术债的记录动作；不新增 PRD 未要求的技术债。

每个 `TD-*` 必须直接追溯到 PRD 明示条款或 `USER_DECISION`；需求台账、STEP 或代码基线等派生来源不能自行把实现缺口升级为技术债。发现无直接来源的 `TD-*` 是确定性错误：`orchestrated`/`review-repair` 删除该技术债编号和映射，保留其真实的实现缺口或风险分类后完整复审；`review-only` 返回 `FAILED_VALIDATION`。

### 维度 9：代码事实核查

核实 STEP 声称 `existing` 的文件、函数、符号、接口和结构。总控模式还要核对每项的 `source_id` 指向实际来源清单，`locator` 能在该文件中定位，显示值与定位符一致。未读取代码时列为待核查，不凭印象判断。

若 STEP 仍依赖“现有查询入口、路由、下载约定、构建或测试命令”等尚未定位的项目事实，不得写成“按既有约定”后给出无风险 `PASS`：能在实施前用明确停止门安全发现时至少返回 `PASS_WITH_RISKS`；它决定核心可行性或验收方式时返回 `DOCUMENT_ONLY` 或 `BLOCKED`。

## 修正分类

### 可自动修正

仅在证据给出唯一答案时修正：

- 编号、格式、断链引用和确定性映射错误；
- PRD 唯一明确的遗漏、冲突或排除项；
- 仓库唯一证实的路径、符号或现有行为；
- 完全重复且删除后不损失映射的 STEP；
- 明确前置条件唯一推出的依赖边。

### 必须阻断

- PRD 内部冲突或缺少业务值；
- 多个合理的业务语义或高影响架构方案；
- 未知依赖或无法唯一解决的依赖环；
- 安全、权限、数据丢失、不可逆迁移、合规或公开接口破坏；
- 缺少判断所必需的代码或契约。

“按你的最佳判断”“按行业惯例”或时间压力都不是具体 `USER_DECISION`。若同一批问题既含确定性错误又含业务歧义，可以先修确定性错误，但最终仍返回 `BLOCKED`，不得生成 `steps-verified.md`。

## 修正闭环

`review-repair` 与 `orchestrated` 执行：

1. 保存用户原文和首次审查结果；
2. 按上述分类修正确凿问题，生成新文件，不覆盖原文；
3. 记录逐项 Diff：原内容、修正内容、来源证据、影响映射；
4. 重建需求映射、验收映射和依赖关系；
5. 从 PRD、代码/契约和完整修正版重新执行九维完整复审；
6. 通过则产出 `steps-verified.md`，否则记录阻断并停止。

最多两轮修正。每轮后都做完整复审；同一问题仍出现、问题与证据均未变化，或机械修正无法收敛时停止。语义未决返回 `BLOCKED`，结构/产物校验仍失败返回 `FAILED_VALIDATION`。

首次审查无问题时直接形成验证结论，不制造空修正记录或空 Diff。

## 阶段结果

| 结果 | 使用条件 |
|---|---|
| `PASS` | 完整复审通过且风险列表为空 |
| `PASS_WITH_RISKS` | 完整复审通过，仅有明确非阻断风险 |
| `DOCUMENT_ONLY` | 可完成文档比对，但缺少代码/契约，不能形成验证版 |
| `BLOCKED` | 需要用户业务决定或缺少语义判断来源 |
| `FAILED_VALIDATION` | 结构、映射、依赖或产物在修正后仍未通过 |

在 `review-only` 中，只要发现由现有来源唯一确定的结构、映射、依赖或验收问题，由于本模式不授权修正，当前输入仍未通过，返回 `FAILED_VALIDATION`；不要因“问题可修但本次未修”改判 `DOCUMENT_ONLY`。

`DOCUMENT_ONLY` 只用于没有提供或没有实际读取判断所需的代码/契约来源。仓库中尚未实现 PRD 计划新增的路由、调用点或测试，不等于缺少代码仓；这类已确认的基线缺口按项目事实风险和实施前停止门处理。

只要仍有非阻断风险就用 `PASS_WITH_RISKS`。`PASS`/`PASS_WITH_RISKS` 才能生成 `steps-verified.md`；`DOCUMENT_ONLY` 只能保留暂定版。`BLOCKED` 或 `FAILED_VALIDATION` 不得继续。

## 人类可读报告

`step-audit.md` 至少包含：

1. 九维总览评分；
2. 逐 STEP 问题、严重度和证据；
3. 需求/决策覆盖；
4. 验收覆盖；
5. 技术债与排除项；
6. 依赖与代码事实核查；
7. 首次审查结论；
8. 修正 Diff（适用时）；
9. 完整复审结论、阶段结果、风险和阻断项。

`review-only` 默认只交付报告。`review-repair` 和 `orchestrated` 保留原文、首次报告、修正版及最终报告。使用当前环境可用的本地文件路径或可点击链接交付，不依赖特定的文件呈现工具。

## 自检

- [ ] 九维首次审查完整
- [ ] 每个问题都有来源和严重度
- [ ] 只修了唯一可证实的问题
- [ ] 原文、首次审查和 Diff 均保留
- [ ] 每轮后从完整来源重新复审
- [ ] 修正不超过两轮
- [ ] 业务歧义没有被“最佳判断”代替
- [ ] 只有完整通过才生成 `steps-verified.md`
- [ ] 已返回五种结果之一并在本阶段停止
