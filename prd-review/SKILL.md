# PRD 需求与代码审查

## 手动触发

仅在用户显式调用 `$prd-review` 或明确点名 `prd-review` 时使用。普通谈话中提到 PRD、上传需求文件或请求一般建议，都不自动触发。

## 核心原则

把 PRD 转换为有来源、可追踪的审查结论。代码用于核实当前基线和可行性，不能取消、改写或覆盖 PRD 的明确要求；只有 PRD 明确要求“保持现有逻辑”时，代码才补充该条款的具体事实。

## 执行模式

- `standalone`：用户直接调用本 Skill。默认先复述理解；若用户尚未确认输入，再等待一次确认。若用户已明确确认当前 PRD 并要求直接完整审查，不重复确认。输出本阶段完整报告后结束，不自动进入下一阶段。
- `orchestrated`：由 `$prd-delivery-harness` 在 Phase 0 读取本 Skill 后执行。跳过重复的流程确认，完成门禁后把产物和阶段结果交回总控；不自行调用下一阶段。

两种模式都不能跳过真正的业务确认。PRD 存在多个合理业务解释，或需要用户选择业务值、权限、状态、范围，以及安全、数据丢失、不可逆迁移、合规、公开接口破坏等高影响决策时，返回 `BLOCKED`。

## 输入

支持：

- PDF、Word（`.docx`）、Markdown（`.md`）和纯文本文件；
- 对话中的文本粘贴；
- 用户给出的本地路径或可访问仓库链接；
- 当前工作区中可验证的项目规则、契约和代码。

缺少 PRD 正文时停止并说明缺少项。缺少代码但仍能审查文档时继续，代码相关结论标为未核实，并返回 `DOCUMENT_ONLY`。

## 事实来源

冲突时按以下优先级处理：

1. `USER_DECISION`：用户已经明确确认的补充决定；
2. `PRD`：当前 PRD 明确条款；
3. `CONTRACT`：PRD 明确引用或项目已有的契约；
4. `REPO_BASELINE`：当前仓库可验证事实；
5. 项目既有规范；
6. 派生文档。

具体事实使用统一标签：`USER_DECISION`、`PRD`、`CONTRACT`、`REPO_BASELINE`、`RUNTIME`、`PLANNED`、`UNVERIFIED`。标签表示证据来自哪里，而不是事实谈论什么：用户口述“仓库中存在某路径或符号”仍是 `USER_DECISION`；只有本轮实际读取并核实的文件、路径或符号才能标为 `REPO_BASELINE`。没有 `RUNTIME` 证据时，只能描述仓库基线，不声称已验证线上行为。不得自行创造业务字段、错误码、状态值、优先级或业务顺序。

验收只约束某个请求、系统层级或可观察输出时，只能登记对该对象直接声明的行为。“非管理员直接请求导出返回 HTTP 403”只建立服务端鉴权与响应约束；除非 `PRD` 或 `USER_DECISION` 明示 UI 或客户端行为，不得在需求台账、报告、影响范围或建议中改写为按钮隐藏/禁用、仅管理员显示/提供动作、非管理员 UI 不提供动作或客户端拦截。仓库中的 UI 惯例可以标为 `REPO_BASELINE`，但没有上述需求来源时，不得把它映射为对应需求或验收的必须行为。

## 审查流程

### 1. 读取并理解 PRD

首次读取时建立 `requirements-ledger.md`，至少包含：

- 需求 ID、原文摘要与来源位置；
- 验收 ID、通过条件与来源位置；
- 排除项；
- PRD 明示的技术债；
- 冲突、歧义和待核实项。

保留 PRD 已有 ID；对未编号但必须追踪的约束统一分配 `CSTR-*`，不得升级为新的 `RQ-*`。排除项继续使用 PRD 原 ID；没有原 ID 时使用 `OUT-*`。

只有 PRD 明确标为技术债的条目，或用户以 `USER_DECISION` 明确确认的技术债，才能进入技术债清单或分配 `TD-*`。仓库中“尚未实现本 PRD 要求的端点/页面/测试”等差异只是实现缺口、计划工作或风险，不得升级为技术债，也不得仅凭派生台账获得 `TD-*`。

`standalone` 需要复述时使用：核心目标、主要改造内容、涉及范围、不确定点。不要把普通实现选择包装成业务歧义。

### 2. 定向读取项目事实

根据 PRD 中的页面、模块、实体、字段、流程和接口，先发现项目规则与契约，再定向搜索相关路由、模型、服务、控制器、组件和测试。记录实际文件与符号证据；找不到时标为 `UNVERIFIED`，不能猜测。

### 3. 完整审查

检查：

- PRD 内部冲突、遗漏、边界和可测性；
- PRD 与代码基线在接口、数据、权限、兼容性上的差异；
- 实现可行性、安全性、业务逻辑和影响范围；
- 明确要求、验收、禁止项和技术债是否都有处置结论。

### 4. 第二次来源覆盖检查

从 PRD 开头重新检查编号条款、列表项、表格行和验收项。每一项必须进入需求台账，或明确标为背景、重复、冲突或不适用。分别汇报：

- PRD 来源条目的处置情况；
- 需求覆盖情况；
- 验收覆盖情况。

不得宣称“业务语义绝对 100% 正确”。

### 5. 返回阶段结果

只使用以下结果：

| 结果 | 使用条件 |
|---|---|
| `PASS` | 来源、语义和必要代码事实充分，无阻断项且风险列表为空 |
| `PASS_WITH_RISKS` | 必要来源已实际核验，但仍有证据明确的非阻断风险 |
| `DOCUMENT_ONLY` | 可完成文档审查，但未实际读取判断所需的代码或契约；用户口述的仓库事实不能代替核验 |
| `BLOCKED` | 需要用户业务决定或缺少判断所必需的来源 |
| `FAILED_VALIDATION` | 产物不可读、结构失败，或来源变化使旧结果失效 |

`standalone` 在本阶段结束；`orchestrated` 只把结果交回总控。`BLOCKED` 或 `FAILED_VALIDATION` 不得继续。只要报告列出非阻断风险，结果就必须是 `PASS_WITH_RISKS`，不能同时写 `PASS`。未实际读取必要代码时必须是 `DOCUMENT_ONLY`，总控只能走暂定分支。

已读取部分代码但核心集成入口、路由、查询调用点或验证命令仍只能留待实施时发现时，不得因其标为 `PLANNED` 就给无风险 `PASS`；能安全延后并设停止门时使用 `PASS_WITH_RISKS`，无法判断可行性或验收时使用 `DOCUMENT_ONLY` 或 `BLOCKED`。

## 人类可读报告

保留完整 Markdown 报告，按需要包含：

1. 需求实现综合评估表：现状、PRD 要求、可行性、风险；
2. PRD 方案与当前基线对比；
3. 需要修改的页面、组件、接口、数据、逻辑、配置或权限范围；
4. 仅在复杂流程确有帮助时提供 Mermaid 图；
5. 冲突与问题清单，区分 PRD 内部问题和 PRD/代码差异；
6. 待确认问题，包含互斥选项、优缺点、推荐理由和业务场景 Demo；
7. 来源覆盖、需求覆盖和验收覆盖结果；
8. 阶段结果、非阻断风险和阻断项。

问题选项必须来自可解释的候选方案，推荐不等于替用户决定。无问题的章节写明“本次审查未发现明显问题”，不留空表。

`orchestrated` 还需返回给总控：台账路径、来源摘要、阶段结果、风险与阻断项。结构约定以总控的 `references/pipeline-contract.md` 为准；本 Skill 不写业务代码或正式 Contract。

## 自检

- [ ] PRD 来源条目完成两次检查
- [ ] 需求、验收、排除项和技术债均有处置
- [ ] 事实带来源标签，判断与事实分开
- [ ] 代码基线未反向改写 PRD
- [ ] 未把 `REPO_BASELINE` 表述为 `RUNTIME`
- [ ] 真正的业务歧义已阻断，普通实现细节未制造额外确认
- [ ] 已给出五种结果之一
